# Database Setup

## Oracle Connection

Configure these environment variables for the application run configuration:

- `ORACLE_DB_URL`, for example
  `jdbc:oracle:thin:@//localhost:1521/YOUR_SERVICE_NAME`
- `ORACLE_DB_USERNAME`
- `ORACLE_DB_PASSWORD`

Replace the example service name with the actual Oracle service name.

## Initial User Accounts

Set all six `TRUSTVAULT_*` account environment variables described in the
README. The initializer stores BCrypt password hashes, not raw passwords.
It does not overwrite existing users, and it does not create default
accounts when credentials are absent.

## Initial Table

The first entity maps to `TV_USERS`, with these fields:

- `ID`
- `EMAIL`
- `FULL_NAME`
- `PASSWORD_HASH`
- `ROLE_NAME`
- `ENABLED`
- `CREATED_AT`

Local development uses Hibernate schema updates. Production schema changes
should move to reviewed, versioned database migrations before deployment.

# TrustVault Database — Initial Document Model

## TV_DOCUMENTS

Stores document metadata. File contents are stored separately in private file storage.

| Column | Purpose |
|---|---|
| ID | Primary key generated by `TV_DOCUMENTS_SEQ` |
| TITLE | Display title |
| ORIGINAL_FILENAME | Original uploaded filename |
| STORAGE_KEY | Server-generated storage identifier; unique |
| CONTENT_TYPE | Validated content type |
| SIZE_BYTES | File size in bytes |
| OWNER_ID | Foreign key to `TV_USERS.ID` |
| CREATED_AT | Document creation timestamp |

## Security notes

- Ownership is associated with an existing `TV_USERS` record.
- The client must not be allowed to assign or change `OWNER_ID`.
- File contents must not be placed in a public static directory.
- Document metadata alone does not grant access to the underlying file.
- Named-user permissions and audit events will be added in subsequent implementation steps.

**Status:** Initial entity definition; verify the Oracle schema and application startup before treating this model as deployed.

## Database Integrity and Security

- Enforce appropriate database constraints, including primary keys, foreign keys, and uniqueness requirements, in accordance with the entity definitions.
- Validate required fields before persisting records.
- Store passwords only as secure BCrypt hashes; never store plaintext passwords.
- Generate storage identifiers on the server and keep document contents outside public web directories.
- Enforce document ownership and named-user permissions in the application before allowing document access or downloads.
- Record security-relevant actions in an audit trail, including the acting user, document, action, and timestamp, once audit logging is implemented.

## Audit Logging

TrustVault records successful document download events in the `TV_AUDIT_LOGS` table.

### Create Audit Table

```sql
CREATE TABLE TV_AUDIT_LOGS (
    ID NUMBER(19) PRIMARY KEY,
    DOCUMENT_ID NUMBER(19) NOT NULL,
    USER_ID NUMBER(19) NOT NULL,
    ACTION VARCHAR2(50) NOT NULL,
    OUTCOME VARCHAR2(20) NOT NULL,
    EVENT_TIME TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,

    CONSTRAINT FK_TV_AUDIT_DOCUMENT
        FOREIGN KEY (DOCUMENT_ID)
        REFERENCES TV_DOCUMENTS(ID),

    CONSTRAINT FK_TV_AUDIT_USER
        FOREIGN KEY (USER_ID)
        REFERENCES TV_USERS(ID)
);
```

### Create Audit ID Sequence

```sql
CREATE SEQUENCE TV_AUDIT_LOG_SEQ
    START WITH 1
    INCREMENT BY 1
    NOCACHE;
```

### Verify Audit Records

```sql
SELECT
    ID,
    DOCUMENT_ID,
    USER_ID,
    ACTION,
    OUTCOME,
    EVENT_TIME
FROM TV_AUDIT_LOGS
ORDER BY EVENT_TIME DESC;
```

### Audit Event Fields

| Column | Description |
|---|---|
| `ID` | Unique audit event identifier |
| `DOCUMENT_ID` | Document associated with the event |
| `USER_ID` | User associated with the event |
| `ACTION` | Action performed, such as `DOCUMENT_DOWNLOAD` |
| `OUTCOME` | Result recorded, such as `SUCCESS` |
| `EVENT_TIME` | Time the audit event was recorded |

### Notes

- The foreign-key references assume the existing tables are named `TV_DOCUMENTS` and `TV_USERS`, with primary keys named `ID`.
- The sequence name must match the sequence configured in the `AuditLog` entity.
- These scripts create the audit table and sequence; they do not recreate existing application tables.
- Audit records should be treated as append-only by the application. Database privileges should restrict who can modify or delete them.
